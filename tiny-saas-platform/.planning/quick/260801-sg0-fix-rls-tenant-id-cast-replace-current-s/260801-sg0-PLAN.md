<objective>
Fix the RLS `tenant_id` cast bug (`current_setting('app.tenant_id', true)::uuid` throws `invalid input syntax for type uuid` when the GUC resolves to `''` instead of `NULL`), add the missing `FORCE ROW LEVEL SECURITY` on `tenants`/`users`/`tiny_credentials`, and grant `SELECT` to `authenticated` on those same three tables — consistent with the confirmed Supabase Auth native model (frontend queries Postgres directly as `authenticated`, no custom JWT/service_role proxy layer).

**Migration strategy decision — new corrective migration, NOT an in-place edit of `20260729003512_init_schema.sql`:**
`.planning/STATE.md` (Decisions log, and the `[Phase ?]` line about repairing "a pre-existing orphaned remote migration-history entry (20260729003512_init_schema, real tenants/users/tiny_credentials tables)") confirms this migration already ran against the live Supabase project — plan 01-02 was unblocked specifically to push it, and the `tenants`/`users`/`tiny_credentials` tables it creates already exist remotely. `supabase db push` tracks applied migrations remotely by filename/version timestamp; once a version is recorded as applied, editing that file's contents in place does **not** cause it to be re-applied — it only makes the local file diverge silently from what's actually live, which is strictly worse than the current bug. (The file also happens to show as untracked `??` in `git status` right now — that is a git-tracking gap, not evidence the migration wasn't pushed; Supabase's migration-history table is independent of git.) The safe path is a new migration file with a later timestamp that `ALTER POLICY`/`ALTER TABLE`/`GRANT`s the existing objects into the corrected state.

Purpose: `app.tenant_id` resolves to `''` (not `NULL`) in some pooled-connection paths (e.g. after `RESET` or a Transaction Pooler connection handoff between statements), and the direct `::uuid` cast on `''` throws instead of denying access — the opposite of the documented fail-closed intent. Independently, `tenants`/`users`/`tiny_credentials` were created via raw migration SQL, which (unlike Studio-created tables) does not auto-grant `authenticated` anything, and none had `FORCE ROW LEVEL SECURITY`, so the table-owner role could bypass RLS entirely.

Output: a new `supabase/migrations/*_fix_rls_tenant_id_cast_and_grants.sql` applied to the live project, a reusable `scripts/verify-rls-tenant-fix.ts` diagnostic confirming the fix live, and consistency fixes in the two doc files and one SQL example file that still show the old cast pattern.
</objective>
