# Quick Task 260802-hvz: Real sync-enqueue/sync-worker Products Sync Pipeline

**Replaced Phase 1's `{kind:"ping"}` placeholder pipeline with a real, proven watermark-driven products sync engine: sync-enqueue (LEFT JOIN tiny_credentials/sync_watermarks producer) -> pgmq sync_work queue -> sync-worker (read+archive consumer, per-tenant Vault token resolution, bronze/silver/watermark transaction, 401->expired handling) -> tiny-mock-produtos, with a local end-to-end test proving enqueue, watermark suppression, cross-tenant isolation, and the 401 path all work against a real local Postgres/Edge Functions stack.**

## Accomplishments

- Three new migrations: `products`/`sync_watermarks`/`raw_tiny_payloads` tables with fail-closed RLS (`ENABLE`+`FORCE`, `NULLIF(...)::uuid` policy, matching the pattern already fixed for `tenants`/`users`/`tiny_credentials`); `pgmq_public.read`/`archive` wrapper functions (service_role-only); a second, independent `pg_cron` job (`sync-worker-trigger`, every 3 min) alongside the untouched 15-min `sync-enqueue-trigger`.
- `sync-enqueue` rewritten: one joined `tiny_credentials LEFT JOIN sync_watermarks` query selects connected tenants with a null/stale (>15min) products watermark; each gets one `pgmq_public.send` call, wrapped in its own try/catch; returns `{enqueued, tenant_ids}`.
- `sync-worker` rewritten: `pgmq_public.read` (60s visibility timeout, batch capped at 15) + explicit `archive` replacing Phase 1's `pop`; `tenant_id`/`resource_type` destructured fresh inside the per-message loop body (never hoisted — the concrete mitigation for the highest-consequence trust boundary in this plan); per-tenant Vault access-token resolution; bronze+silver+watermark written in one transaction per tenant, watermark only advancing after that transaction commits; 401 marks `tiny_credentials.status='expired'` and archives; other errors leave the message un-archived for visibility-timeout redelivery; every iteration wrapped in its own try/catch.
- New mock Edge Function `tiny-mock-produtos`: simulates Tiny's `GET /produtos` v3 endpoint, embeds the caller's own access-token tag (last 8 chars) into every returned product's `nome` — the mechanism that makes cross-tenant leakage provable, not just tenant_id-column-checkable. `?simulate=401` test scaffold for the expired-token path.
- `scripts/test-products-sync-pipeline.ts`: local-only e2e proof (hardcoded `127.0.0.1:54322`/`54321` guards, dynamic service-role key fetch via `supabase status -o env` with its own guard) proving, against a real local stack: Tenant A enqueue -> queue -> worker -> bronze/silver/watermark; watermark suppression on immediate re-enqueue; Tenant B's independent cycle with zero cross-tenant contamination in either direction. Ran three times independently, all exit code 0.

## Decisions Made

Per this plan's `<output>` instruction, both decisions flagged in PLAN.md's `<objective>` are restated here verbatim in substance for STATE.md's Decisions log:

**1. Duplicate-enqueue design decision — allowed, not guarded.** `sync-enqueue`'s pending-tenant query does **not** check `sync_work` for an already-in-flight message before sending. Rationale: the watermark (`sync_watermarks.last_synced_at`) already prevents re-enqueueing once a cycle **completes** — the only duplicate-risk window is a still-in-flight message from the current, not-yet-finished cycle. A "check pending" query would add a second round-trip per invocation, working against the Edge Function 2s CPU budget, and introduces its own check-then-enqueue TOCTOU race unless wrapped in row-level locking (disproportionate complexity for the problem). The cost of a duplicate is small and bounded: one extra `pgmq` message, one extra (mocked, free) Tiny API call, one extra `ON CONFLICT DO UPDATE` that is a near-no-op since the data hasn't changed — `docs/03-INTEGRACAO-TINY-ERP.md` §3 already accepts this class of redundancy by design. Structurally, the worker cron (every 3 min) runs far more often than the enqueue cron (every 15 min), bounding how often duplicates can even occur. `pgmq_public.read`'s visibility timeout already prevents a *second worker invocation* from double-processing the *same* message concurrently — the residual risk accepted here is strictly "enqueue happens again before the first message is archived," never "the same message gets processed twice."

**2. pgmq vs. simple-table architecture conflict — proceeded on pgmq per this session's explicit brief instruction, flagging the tension rather than silently resolving it.** `.planning/ROADMAP.md`'s Phase 3 entry, `docs/01-ARQUITETURA.md` §7, and `docs/02-MODELO-DE-DADOS.md` §5 all document a confirmed architecture decision (2026-08-01): migrate the webhook/sync queue mechanism from `pgmq` (built in Phase 1) to a simple Postgres table with polling, explicitly **before** Phase 3 (sync engine) depends on it. This session's task brief explicitly instructed the opposite — build directly on the existing `pgmq`/`pgmq_public` infrastructure, framing the queue-mechanism migration as out of scope. This plan proceeded on `pgmq` as instructed (also matching Phase 1's own forward-looking note in `01-04-SUMMARY.md` anticipating Phase 3 *extending* `pgmq`, not replacing it), but this **deepens the real dependency on `pgmq`** that the 2026-08-01 decision wanted to avoid creating. **Flag for the user/orchestrator:** after this session, `STATE.md`'s Pending Todo and `ROADMAP.md`'s Phase 3 pre-requisite line need an explicit human decision — either (a) formally reverse the 2026-08-01 decision and keep `pgmq` permanently (this session's real, working usage is direct evidence for that outcome), or (b) still plan the `pgmq` -> `webhook_queue` migration as a follow-up, which would now need to migrate this session's real usage too, not just Phase 1's placeholder. This plan does not decide (a) or (b); it only proceeded under the explicit, repeated instruction given for this session.

**3. `pop` -> `read`+`archive` technical correction.** The task brief's own worded description of the consumer step described `pgmq`'s `read`+visibility-timeout semantics (crash-safe, automatic retry), not `pop`'s actual delete-on-read, at-most-once behavior. This plan implements the semantics the brief actually needed, using `pgmq_public.read` + a new `pgmq_public.archive` wrapper — matching Phase 1's own explicit forward note that this swap is Phase 3's job.

**4. No Vault wrapper function exists — `sync-worker` follows `tiny-oauth-callback`'s direct `vault.decrypted_secrets` query pattern**, since no such wrapper exists anywhere in this codebase.

- **Local `supabase_edge_runtime` container instability under manual `docker rm -f` + `supabase start`:** discovered that manually removing a single running container (`docker rm -f supabase_edge_runtime_...`) and then calling `supabase start` left the CLI in a confused state where it silently stopped attempting to recreate that one container on subsequent `start` calls (zero `docker events` for it), even though `docker ps -a` showed it entirely absent. Going forward, always use full `supabase stop`/`start` cycles rather than partial `docker rm`/`restart` of individual containers when a local Docker Desktop/Supabase CLI project needs its Edge Functions to pick up an updated `.env`.
