<objective>
Prove the single highest-risk item in this phase first: a Deno Edge Function deployed to the real
Supabase project, reachable at a public URL with no auth required, that successfully queries
production Postgres through the Transaction Pooler (port 6543) using `postgres.js` with
`{ prepare: false }` — the exact connection discipline that, done wrong, caused the prior
`tinysaas` project's production incident (commit `55b0f80`) under the old Session-Pooler/psycopg
stack, and would recreate the same failure class here under a different runtime if the pooler mode
or prepared-statement flag were wrong.

Purpose: De-risk the pooler/driver connection method before any other Phase 1 work (migrations,
Cron, Queue) is built on top of it, per `01-CONTEXT.md`'s explicit framing of this phase's purpose.
Per D-05, Supabase Realtime is not used anywhere in this phase or plan — the health check and every
later plan in this phase rely solely on request/response Edge Functions and the Cron+Queue pipeline,
never a Realtime subscription.
Output: A deployed, publicly-reachable `health` Edge Function; a reusable `_shared/db.ts` Postgres
client factory; a reusable `scripts/smoke-test-db.ts` connection script (consumed unchanged by
CI in plan `01-02`); and automated Deno tests proving both the health endpoint and the
prepare:false pooler-safety claim.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Internet -> `health` Edge Function | Public, unauthenticated (`verify_jwt=false`) — untrusted callers reach this handler directly |
| Edge Function -> Supabase Postgres | Crosses via the Transaction Pooler (Supavisor), authenticated with the pooler-specific `postgres.<project-ref>` user, TLS in transit |
| Local dev machine / future CI -> Supabase | Crosses via the `DATABASE_URL` secret, held only as an env var, never committed |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|------------------|
| T-01-01 | Information Disclosure | `health/index.ts` error path | high | mitigate | Catch block logs only the caught `err` object via `console.error`; never interpolates or logs `DATABASE_URL`/`connectionString`; response body on failure is the fixed literal `{"status":"error"}`, never a stack trace or raw error message |
| T-01-02 | Tampering | `_shared/db.ts` connection-string construction | critical | mitigate | Reads `DATABASE_URL`/`SUPABASE_DB_URL` as one opaque string; the file never splits into host/user/password and never rebuilds a connection string from parts — the exact `55b0f80` bug class this phase exists to prevent |
| T-01-03 | Denial of Service | Public unauthenticated `/health` endpoint | medium | accept | Health checks run a single lightweight `select 1` through the pooled connection; Supabase free tier's 500k invocations/month cap is generous for expected polling cadence at this project stage (pre-revenue, low traffic); no rate limiting added this phase — revisit if abuse is observed |
| T-01-SC | Tampering | npm installs (`postgres`, `supabase` CLI) | high | mitigate | Both already verified in 01-RESEARCH.md's Package Legitimacy Audit (Approved: high weekly downloads, official source repos); versions pinned in `deno.json` import maps (`postgres@3.4.9`) rather than left unpinned |

</threat_model>
