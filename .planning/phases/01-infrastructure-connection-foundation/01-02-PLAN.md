<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| GitHub Actions runner -> Supabase (DB + CLI) | CI job authenticates via repo secrets (`DATABASE_URL`, `SUPABASE_ACCESS_TOKEN`, `SUPABASE_DB_PASSWORD`) injected as env vars |
| PR from an external contributor -> `deploy` job | Only relevant once the repo has external contributors; currently solo-maintained |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|------------------|
| T-02-01 | Information Disclosure | `ci.yml` smoke-test/deploy steps | high | mitigate | Secrets referenced only via `${{ secrets.X }}` GitHub Actions injection, never hardcoded in the YAML; `scripts/smoke-test-db.ts` (plan 01-01) never logs the connection string, only a fixed success message |
| T-02-02 | Tampering | Fork-originated pull requests modifying `ci.yml` | medium | accept | GitHub's default behavior withholds repository secrets from workflow runs triggered by fork PRs; repo is solo-maintained and pre-revenue per PROJECT.md — revisit if the repo opens to external contributors |
| T-02-03 | Elevation of Privilege | `deploy` job running `supabase db push`/`functions deploy` with full-account `SUPABASE_ACCESS_TOKEN` | high | mitigate | `deploy` job is gated `if: github.ref == 'refs/heads/main'` so no branch or PR other than main can trigger a production migration or deploy; the access token exists only as a GitHub encrypted secret |
| T-02-SC | Tampering | GitHub Actions supply chain (`supabase/setup-cli@v1`, `denoland/setup-deno@v2`, `actions/checkout@v4`) | medium | mitigate | All three are pinned to major-version tags from verified official organizations (`supabase`, `denoland`, `actions`), matching 01-RESEARCH.md's documented reference workflow exactly |

</threat_model>
